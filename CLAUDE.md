# CLAUDE.md — Cafelytic

A pointer file for Claude Code sessions working in this repo. Not user-facing.

## What this is

[cafelytic.com](https://cafelytic.com) — a coffee water / brew recipe calculator. Multi-page TypeScript (vanilla, no framework) bundled by Vite, shipped two ways: as a web app deployed to GitHub Pages on every push to `main`, and as native iOS + Android apps (Capacitor) that wrap the same `dist/` build. The classic-JS → TypeScript migration is complete; `theme-init.js` is the one intentional classic script (see Verification stack below).

## Stack

- **Frontend**: TypeScript modules under `src/`, no framework, bundled by Vite (`vite.config.mts`). Each page loads the single module entry `<script type="module" src="/src/lib/legacy-globals.ts">`, which imports the lib + component modules and `Object.assign`s their exports onto `window` for the inline page `<script>` blocks (and e2e page-context reads); index.html additionally loads `src/components/script.ts` (the calculator orchestrator) as its own entry. The one classic script left is `theme-init.js`, a render-blocking `<head>` primer.
- **Backend**: Supabase (Postgres + Auth). Client created in `src/lib/supabase-client.ts` (bundled from the `@supabase/supabase-js` npm package; was a CDN `<script>` pre-migration); migrations in `supabase/migrations/`. Server-side Edge Functions live in `supabase/functions/`: `estimate-water` (JWT-gated, per-user quota), `submit-support` (the Support-page contact form; emails info@cafelytic.com via the Resend API, `verify_jwt = false` so logged-out users can reach support, needs the `RESEND_API_KEY` secret), and `mcp` (the MCP server that lets a user connect an AI app to their own account; OAuth sign-in through Supabase Auth, `verify_jwt = false` because the function verifies the user JWT itself; see [MCP.md](MCP.md)). **Claude does not deploy functions** — the user runs `supabase functions deploy <name> --remote=srlwgayrxzamxlodpsrq` after setting secrets and confirms its prompt, same as the `db push` gate.
- **Deploy (web)**: push to `main` → GitHub Actions runs the `deploy` job in [.github/workflows/ci.yml](.github/workflows/ci.yml), which builds `dist/` via Vite and publishes to Pages. Pages source must be set to "GitHub Actions" in repo settings (one-time setup, done in PR (c)). The `e2e` job is serialized repo-wide (a `concurrency` group) because its signed-in specs share one prod test account. `main` is guarded by the `main: require CI` ruleset: six required checks (`typecheck-and-test`, `e2e`, `edge-functions`, `ios-build`, `android-build`, `CodeRabbit`), no force-push or deletion; repo admins can bypass (direct release pushes). Merged head branches auto-delete. The `deploy` job's freshness step skips (with a notice) when any newer commit has already deployed to `github-pages` (full deployment history, `SUCCESS` or `INACTIVE`) and fails the job if that history can't be read; the `pages` group uses `queue: max` so a re-run can't cancel a newer pending deploy. Runs created before this guard existed re-run without it or the queue (re-runs use the original workflow file), so never re-run those; a newer push's guarded run supersedes them.
- **Dependencies**: [.github/dependabot.yml](.github/dependabot.yml) opens weekly grouped PRs for npm packages and the SHA-pinned GitHub Actions (all workflow actions are pinned to commit SHAs with a `# vX.Y.Z` comment). `@capacitor/*` bumps also need `npx cap sync` output committed; Dependabot PRs get no Actions secrets, so signed-in e2e skips on them.
- **Native (iOS + Android)**: Capacitor wraps the same `dist/` build (`capacitor.config.ts`; appId `com.cafelytic.app`). There is intentionally no `server.url`, so the native app loads the bundled `dist/` from inside the app (Capacitor serves it at `capacitor://localhost` on iOS and `https://localhost` on Android, the two origins the CSP in `partials/head-top.html` allows) rather than proxying cafelytic.com. The iOS shell uses Swift Package Manager (no CocoaPods, no `.xcworkspace`). CI compile-checks both shells on every push via [.github/workflows/native.yml](.github/workflows/native.yml): `ios-build` runs an unsigned `xcodebuild` against the simulator SDK on a macOS runner, `android-build` runs `gradlew assembleDebug` — neither signs nor uploads. (ci.yml's `typecheck-and-test` job also runs `npx cap sync android --inline` as a fast scaffold-drift check.) Signed store builds are produced and uploaded locally via `scripts/upload-testflight.sh` (iOS/TestFlight) and `scripts/upload-play-internal.sh` (Android/Play).
- **Dev server**: the `dev` config in `.claude/launch.json` runs `vite` on port 8080 (the Vite dev server, which transpiles the TS modules on the fly). This is what the desktop app's browser pane launches via `preview_start` with the `dev` config. A second config, `dist-preview`, runs `vite preview` on port 4173 and serves the built `dist/` (run `npm run build` first), for checking build-only behavior in the browser pane.

## Verification stack

The multi-phase rollout below is complete. It is kept as a record of how the stack was built (the plan file that tracked it was local to the Claude Code harness and no longer exists).

- **Phase 1** ✅ — CodeRabbit (PR review) + Sentry (runtime errors).
- **Phase 2** ✅ — Playwright MCP + `e2e/` runbooks.
- **Phase 3** ✅ — Vite + TypeScript strict bundling. **Infrastructure landed**: Vitest + Playwright + ESLint/`tsc --noEmit`, the Vite scaffold (PR a), the dev-server + TS test migration (PR b), the Pages deploy cutover (PR c), the storage/sync move to `src/lib/*.ts` plus the `legacy-globals.ts` bridge (PR d), and the first UI slice (ui-shared.js + login-modal.js → `src/components/*.ts`, PR e). `supabase-client` and `sentry-init` have likewise landed as `src/lib/*.ts`. **The classic → TypeScript migration is complete**: the constants and metrics layers now live at `src/lib/constants.ts` and `src/lib/metrics.ts` (typed modules; `legacy-globals.ts` `Object.assign`s both onto window for the inline page scripts and e2e page-context reads). `theme-init.js` is the one intentional permanent classic — a render-blocking `<head>` primer (loaded via `partials/head-bottom.html`) that a deferred ES module would break (it would run after first paint and reintroduce FOUC plus the native inter-page flash; `smoke-index.spec.ts` guards against converting it). It is `@ts-check`'d + linted, so it is an intentional classic, not an outstanding migration.
- **Native rollout** ✅ (separate effort, after the verification stack above) — the app now also ships as native iOS + Android via Capacitor; see the **Native (Capacitor)** row in the file map and the **Native** bullet under Stack. `capacitor.config.ts` comments trace the relevant PRs (through "PR h").

## Verifying changes

When you (Claude) make a code change, verify it using this cheat sheet:

| Change | Tool | Notes |
|---|---|---|
| Pure logic (calc, storage serialization) | `npm test` (Vitest), plus `npm run typecheck` / `npm run lint` | Default first check. `npm run typecheck` (`tsc --noEmit`) covers `src/**/*.ts` + `theme-init.js`; `node --check theme-init.js` is a quick syntax check for that one classic. |
| Rendering a single page, single flow | **Desktop app browser pane** (`preview_start` → `dev`, then `read_page` / `javascript_tool` / `read_console_messages`) | Fast, runs against the local dev server. First-line default. |
| Multi-page flows, multi-context sync, creator-gated branches | **Playwright MCP** (`mcp__playwright__*`) | Run a runbook from [e2e/](e2e/README.md). Slower, but supports multiple contexts (two-device sync scenarios). The `*.spec.ts` suite runs against `vite preview` (the built `dist/`), so it catches build-only regressions the dev server hides. |
| Native (Capacitor) UI or behavior | **Browser pane / Playwright** with the native platform forced on, or a real simulator/device build | On web, `@capacitor/core` overwrites a naive `window.Capacitor` stub, so force `isNativePlatform()` via a getter/setter shim injected before app scripts run (`addInitScript`). Full native verification needs `npx cap run ios` / `npx cap run android`. |
| Production-only issue (e.g. Sentry wiring, CDN deploy) | `curl` the live URL, then check Sentry Feed | Local previews don't exercise the deployed build or its CDN. |

**Default**: reach for the browser pane first. Escalate to Playwright only when the test requires what it can't do (multiple browser contexts, richer assertion primitives).

### Analytics on localhost

[analytics-init.ts](src/lib/analytics-init.ts) skips loading GA4 when the hostname is `localhost`/`127.0.0.1` (and other loopback addresses: `0.0.0.0`, `::1`, `[::1]`, empty), when `navigator.webdriver` is true, or when `localStorage.cafelytic_no_analytics === "1"`. So local traffic (the dev server, `vite preview`, Playwright, and browser-pane previews of localhost) is excluded automatically by hostname, and webdriver-driven browsers anywhere. Visits to the live site from any other browser, including the desktop app's browser pane, are NOT excluded automatically: opt out first. To exclude a browser on the live site, visit `https://cafelytic.com/?no-analytics=1` once (the script sets the flag and strips the param via `history.replaceState`; subsequent loads run without GA) — `?no-analytics=0` clears it. Devtools fallback: `localStorage.setItem("cafelytic_no_analytics","1")`.

### Sentry on localhost

[sentry-init.ts](src/lib/sentry-init.ts) does not start Sentry on a page loaded over `http://` from a loopback host, so the dev server, `vite preview`, Playwright and CI runs report nothing. To send local events (tagged with the environment `development`), run `localStorage.setItem("cafelytic_sentry_local", "1")` and reload. The native apps load from `capacitor://localhost` (iOS) and `https://localhost` (Android) and report as `production`; do not widen the check to the hostname alone.

## Keeping docs in sync

Several docs in this repo restate facts the code already encodes: file paths, the classic-JS → TypeScript migration status, page selectors and `<h2>` labels, CLI commands, version pins, and store-copy counts. Anything that duplicates the source tree in prose drifts the moment the tree moves — that is how the file map, the e2e runbooks, and SENTRY_SETUP.md all went stale during the migration. When a change makes one of those facts wrong, fix the referencing doc **in the same commit** — don't defer it.

- Before finishing a rename/move/delete of any file under `src/` or the repo root, grep the docs for the old name and update every hit.
- Prefer describing a directory or glob over enumerating individual source files in prose, so there is less to drift.
- Highest-drift docs: **CLAUDE.md** (the File map + Verification-stack notes), **e2e/*.md** runbooks (selectors, `<h2>` labels, paths — the `*.spec.ts` is the source of truth, keep the prose matching), **SENTRY_SETUP.md**, **plans/README.md**, and **store/**.

Two automated backstops catch what slips through:

- **`npm run docs:check`** ([scripts/check-doc-paths.cjs](scripts/check-doc-paths.cjs)) fails if any Markdown doc references a file path that no longer exists. It runs in CI (`typecheck-and-test`) and in the pre-push gate. It checks *paths only*; for intentional non-file references (future/aspirational, gitignored, external plugin source) add the token to its `ALLOWLIST` or append `<!-- doc-paths:ignore-line -->` to the line. Frozen design docs (`plans/`, `SUPABASE_PLAN.md`) are excluded.
- A **CodeRabbit `path_instructions`** entry (`.coderabbit.yaml`) flags PRs that rename/delete source files or rename a user-facing label/selector/command without updating the docs — covering the selectors, labels, status prose, and counts that `docs:check` cannot.

## Supabase safety

Every change that touches `src/lib/sync.ts`, `src/lib/storage.ts`, or row-level-security migrations has user-data risk. The bugs fixed in commits `6d8cd63`, `6464fdb`, `9f89a2e` all slipped past review and cost users recipes. Before merging anything in those files:

1. Run `e2e/smoke-sync.md` (manual, full coverage) and/or `npm run test:e2e -- smoke-sync` (codified subset of Steps 1, 2, 4, 7, 9, 13 covering the load-bearing sync round-trips).
2. Re-read the affected `supabase/migrations/` file end-to-end — do not trust diffs alone.
3. Prefer one extra PR round over a production rollback.

Installed apps keep running the sync code they shipped with, so every change to `src/lib/sync.ts` lives next to old clients on the same account. `tests/sync-mixed-version.test.ts` (part of `npm test`) runs the current module as one device beside `tests/fixtures/sync-v1.2.ts`, a frozen copy of the sync code in the 1.2 and 1.2.1 apps, and fails when the mix loses or brings back more than old devices alone (run it with `SYNC_FLEET_TOTALS=1` to print the totals per fleet). It counts things by presence: a concentrate by its key, a switch by its id. A value reverted inside something that is still there, such as an edit to an existing concentrate's spec, is not measured. `user_settings` and `user_selections` are pushed merged (`pushSingleRows`; `tests/sync-push-merge.test.ts`), in four small steps: `changesSince` names what the device changed since it last synced (fields, map keys, list items); the row is read; `applyChanges` puts those changes onto it, so everything else keeps the cloud's value; and the result is written on condition that the row is unchanged since the read (it reads again if not). One map is merged a level further down: inside `drafts`, the unsaved target edits (`target_draft_ions`, one entry per recipe) are named per recipe (`NESTED_MAPS`, saved names under `drafts.target_draft_ions`), so two devices editing different recipes keep both edits; a 1.2 app still sends its whole map, and a pull still replaces the device's map with the account's. Three supports, each there for one reason. Pushes run one at a time per page (`inPushQueue`), because the diff is only right if the base is the last thing this device got into the row. The names of what a push changes are saved before it sends (`cw_pending_push_*`, names only) and removed when it succeeds, so a save whose answer never arrived is sent again even if the user has since put the value back. And a pull leaves a row's base where it was if the device was holding an unpushed change to that row, so whatever survived the pull is still sent. A pull that does refresh a row's base clears that row's saved names too: the device then holds what the account holds, so the unanswered save is not sent again after such a pull. Two pairs are kept together in favour of the device: the source water key with its values, and the active recipe with the brew method and with that recipe's place on the rail (two rows, two requests, so another writer can still land between them). That pair goes out only on evidence that the device changed it: a row sent whole for want of a base does not count. Before adding a field to either row, check whether it depends on another. Three cases still upsert the whole row with no condition: a device with no readable base for the row, a row that does not exist yet, and the first-login merge's own push. The delete lists go out whole with any change to the selections row, which the pinned sequences in the mixed-version tests depend on (a row pushed only for its half of the active choice leaves them alone); recipe and source water rows, and every pull, still overwrite. This is deliberately not airtight: the comment above `PushFieldKind` in `sync.ts` lists the rare sequences it accepts (a late write landing after a newer one, two tabs saving at once, a stalled request), each no worse than the whole-row push it replaced. Earlier rounds of this change tried to close those and the machinery became its own source of bugs; do not add a guard for one of them without a case that is both worse than the 1.2 sync and plausible in normal use. Never edit the fixture to make a test pass; replace it only when the oldest app still in use ships a newer sync. Only `sync.ts` is frozen: the old device still runs on the current `src/lib/storage.ts` and `src/lib/storage-keys.ts` (key names and categories are pinned by `tests/storage-keys.test.ts`), so a change to what a storage loader returns alters both versions alike and needs a check against a real old build.

The test-account credentials for the spec live in `.env.test` at the project root (gitignored). `CAFELYTIC_TEST_EMAIL` and `CAFELYTIC_TEST_PASSWORD` are loaded by `e2e/smoke-sync.spec.ts` via a small parser at the top of the file (no `dotenv` dep). When credentials are missing, the describe block is `test.skip`-ed so contributors without them still get a green run.

### Migrations

Project is linked to Supabase ref `srlwgayrxzamxlodpsrq` via the CLI; config in `supabase/config.toml`, files in `supabase/migrations/<YYYYMMDDHHMMSS>_<name>.sql`. The first 13 migrations (through `20260425213600_add_brand_tray_and_empirical_profiles.sql`) were applied to prod manually before the CLI was adopted; they're marked applied in `supabase_migrations.schema_migrations` via `migration repair` and should never be re-run.

The repo is on **Supabase CLI 3** (verified on 3.3.0; the `[local_smtp]` section in `supabase/config.toml` needs 2.108.0 or later, so older 2.x can no longer load the file). Two CLI 3 rules shape every command below:

- **Local unless told otherwise.** `db push`, `migration list`, `db reset` and `test db` target the local stack when given no target. A bare `supabase db push` applies to the local stack only and leaves production untouched. For production always write the ref, `--remote=srlwgayrxzamxlodpsrq`: it means the same project in every checkout. A bare `--remote` means the linked project, or the one `SUPABASE_PROJECT_ID` names when that is set, and a worktree is not linked (`supabase/.temp/` is gitignored).
- **Every change to the hosted project asks first, and the default answer is No.** That covers `db push`, `functions deploy` and `secrets set`; the exceptions are the create commands (`projects create`, `branches create`, `orgs create`, `domains create`, `bootstrap`), which default to Yes. A run that cannot prompt (Claude, CI, piped input) fails unless it passes `--yes`. Claude never passes `--yes`, or sets `SUPABASE_YES`, on a command that targets the hosted project. An exported `SUPABASE_YES` answers the prompt for every run in that shell, Claude's included: keep it out of shell profiles, and check it is unset (`echo $SUPABASE_YES`) before a hosted command.

When adding a migration:

1. **Claude:** `supabase migration new <name>`, then edit the generated SQL.
2. **Claude:** `supabase start` (if local stack isn't up), then `supabase db reset` — replays every migration against local Postgres from scratch. Catches name collisions, ordering bugs, broken SQL.
3. **User:** runs `supabase db push --remote=srlwgayrxzamxlodpsrq` against prod from a checkout that contains the migration file (the PR's worktree before the merge; the main checkout after the merge and a pull) and confirms the prompt (the default answer is No, so pressing Enter declines). **Claude does not push**, and never passes `--yes` to a command that targets the hosted project. Production schema changes have cost users recipes before; the human gate is intentional.
4. **Claude:** `supabase migration list --remote=srlwgayrxzamxlodpsrq`, from a checkout that contains the migration file, to confirm the new version appears on both Local and Remote, then run `e2e/smoke-sync.md` against the live site (local DB doesn't catch prod-only issues like extension availability or RLS edge cases).

## Claude Code config

Three layers, least-specific first:

- `~/.claude/settings.json` (machine-global, not in this repo) — broad trust for everyday tools (`git`, `gh`, `npm`, `node`, coreutils) plus ask/deny rails for destructive commands (force-push, `sudo`, recursive deletes).
- `.claude/settings.json` (committed) — project permissions and hooks. Hooks: a SessionStart context primer (branch, recent commits, open PRs), a PreToolUse gate that runs lint, typecheck, `format:check`, `docs:check` and the unit tests before any `git push` and **blocks** the push on failure, a PostToolUse watcher prompt after `gh pr create` (CLI only: skipped when `CLAUDE_CODE_ENTRYPOINT=claude-desktop`, since the desktop app monitors PRs itself, and not meant to stack on `/pr-babysit-merge`'s own loop), and a PostToolUse reminder when sync.ts/storage.ts/migrations are edited (see Supabase safety). `supabase db push` is **denied** here, with or without `--remote` — that's the human gate, not an oversight. So is any `supabase` command that carries `--yes`, the flag that answers CLI 3's hosted-change prompt in advance; the rules do not catch `SUPABASE_YES` set in the environment.
- `.claude/settings.local.json` (gitignored) — machine-specific paths only. Don't accumulate permissions here; broad rules belong in one of the two files above.

Project skills live in `.claude/skills/` (committed): `build-ios`, `build-android`, `pr-babysit-merge`. They travel with worktrees and clones; keep them here, not in `~/.claude/skills/`.
